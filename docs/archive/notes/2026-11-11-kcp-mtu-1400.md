# KCP: 1400-byte MTU instead of 1350

Shipped 2026-11-11. Bulk KCP streams to a 4-vCPU Linux VM moved +3.8% with
6.3% less CPU per MiB, and the default now matches kcp-go, which is what Go frp
uses.

## 1. Why

`frp-core/src/kcp/mod.rs` built the production KCP config with `mtu: 1350`.
kcp-go's default is **1400**, so Go frp has always sent 1400-byte datagrams
while frp-rs sent 1350-byte ones. The MTU is not negotiated: it only decides how
many bytes of KCP payload a datagram carries, so a smaller MTU means strictly
more datagrams — and per-datagram kernel cost is what a KCP bulk stream is
mostly made of (≈80% of frps's samples sit in `udp_sendmsg` on this host,
because the VM is itself containerised and every datagram crosses a veth and the
nftables ruleset).

With `KCP_OVERHEAD` of 24 bytes the payload per segment moves from 1326 to 1376
(−3.6% segments for the same stream).

## 2. Change

- `frp-core/src/kcp/mod.rs`: `default_kcp_config()` and
  `default_kcp_client_config()` use `mtu: 1400`, with the rationale in the
  module docs.
- `frp-core/src/kcp/config.rs`: the pin test now asserts the production MTUs are
  1400 and that `KcpConfig::default()` keeps kcp-go's library default of 1350.
- Comments that quoted 1326-byte segments (`session.rs`, `socket.rs`,
  `kcp_compat.rs`) now quote 1376.

`KcpConfig::default()` is unchanged: it is the conservative kcp-go library
default (`nodelay = 0`, no FEC) and is not on a production path.

## 3. Compatibility

The MTU is per-endpoint and never negotiated, so the only risk is a peer that
cannot *read* a 1400-byte datagram. The driver reads into
`DRIVER_RECV_BUF_SIZE = 1500` (since 2026-08-13) and clamps configured MTUs to
`MAX_KCP_MTU` = 1492 so that `mtu + KCP_WIRE_OVERHEAD` still fits; kcp-go's own
default is 1400. So:

- Go frp peer: sends and accepts 1400-byte datagrams by default.
- frp-rs peer built since 2026-08-13: reads into 1500 bytes.
- frp-rs peer older than that: sized its receive buffer from its own MTU and
  would truncate — the same mixed-MTU hazard the 1500-byte buffer was
  introduced to remove.

## 4. Result

One-flow bulk stream, 2048 MiB, `tcpMux` on, gc VM (4 vCPU AMD EPYC-Milan,
loopback), six interleaved pairs run in **both orders** (three base-first, three
variant-first):

| build | pairs (MiB/s) | mean | CPU ticks per run (frps+frpc) | mean |
| --- | --- | --- | --- | --- |
| mtu 1350 (before) | 63.5 / 62.3 / 62.2 / 61.3 / 63.2 / 62.0 | 62.42 | 7233 / 7284 / 7434 / 7398 / 7239 / 7391 | 7330 |
| mtu 1400 (after) | 65.4 / 65.8 / 66.7 / 63.4 / 64.2 / 63.4 | 64.82 | 7071 / 6937 / 6971 / 7120 / 7021 / 7087 | 6868 |

**+3.8% throughput, −6.3% CPU per MiB**, all six pairs positive. Go frp v0.72.0
measures 98.5 MiB/s on the same host and harness in the same session, so the
residual gap is ~1.5×.

No ping-pong regression: the local `protocol-matrix` run is unchanged within
noise (`kcp-plain` 65.5, `kcp-tls` 71.0, `kcp-tls-mux` 50.8 MiB/s — the same
rows measured 65.5 / 66.4 / 52.1 before this change).

## 5. Limits

- One host, loopback, one flow, twelve runs total. The direction is solid (six
  of six pairs); the magnitude is a bulk-stream figure and does not transfer to
  the ping-pong shape the protocol matrix measures.
- Datagram count re-counted after the change with `/proc/net/snmp`: 590,837 →
  **568,440** inbound and 87,743 → **73,632** outbound per 512 MiB (Go:
  534,678 / 18,424), i.e. 1.06× Go's datagrams instead of 1.1×.
- No Go-vs-Rust pair was taken inside the same six-pair block; the Go reference
  is the adjacent measurement from the same session.
- The CPU figure is a per-run sum of frps and frpc ticks, so its mean is the
  mean of six two-process sums; −6.3% for −3.6% fewer datagrams implies −2.8%
  CPU per datagram, which this change does not explain (fewer, larger
  datagrams also copy more per `sendmmsg`).
- **An earlier note measured this axis as inert** and that result is not
  contradicted here, it is superseded: `docs/archive/notes/2026-11-09-kcp-fec-multiply-tables.md`
  section 3 moved the MTU 1350 → 1400 and saw 20.8 → 20.7 MiB/s, but that run
  was GF-multiply-bound at ~21 MiB/s (the tables and AVX2 landed later). At
  ~64 MiB/s the per-datagram kernel cost dominates, which is why the same axis
  is worth 3.8% now.

## 6. Reproduce

On the VM, `/root/bench/kcp3.sh` runs a peer pair; `/root/bench/kc.sh` is the
same script pinned to the current build, and `/root/bench/kcm.sh` to the
MTU-1400 build:

```sh
bash /root/bench/kc.sh  rs rs cur     1 2048 true
bash /root/bench/kcm.sh rs rs mtu1400 1 2048 true
```

`cpu_s=` prints CPU ticks (`/proc/<pid>/stat` fields 14+15) for frps/frpc. Run
the pairs in **both orders**: this harness has a measurable position bias (the
second process in a pair looks faster), and base-only ordering overstated one
earlier comparison by 6 percentage points.
